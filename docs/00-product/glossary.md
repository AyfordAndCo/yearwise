# Glossary

Status: Draft
Rule: if a word is on this page, use it with the definition here and nowhere else.
If a word is not on this page and you need it, add it here before using it in code.

---

## 1. Identity and tenancy

| Term | Definition |
|---|---|
| **User** | A human with credentials. Owns nothing directly - owns access to workspaces. |
| **Workspace** | The container for all financial, productivity and lifestyle data. Every row in every table belongs to exactly one workspace. |
| **Membership** | The join between User and Workspace, carrying a role. Phase 1 has one membership per workspace; the table exists from day one so sharing is additive, never a migration. |
| **Owner / Editor / Viewer** | Membership roles. Phase 1 renders only Owner. |

**Why `workspaceId` and not `userId`:** "a user's data" and "a workspace's data" are only the same thing while sharing does not exist. Treating them as the same concept is the most expensive shortcut available in this category of app.

## 2. Money

| Term | Definition |
|---|---|
| **Reporting currency** | The single ISO-4217 currency of a workspace (e.g. `SAR`, `USD`). Set at onboarding, changeable in settings. No per-account or per-transaction currency in v1. |
| **Minor unit** | 1/100 of a currency's major unit (1/1000 for `KWD`, `BHD`, `JOD`). All money is stored as an integer count of minor units. |
| **`amountMinor`** | The canonical money field. `BIGINT`. `1234` in a 2-decimal currency means `12.34`. Signed - see section 3. |
| **Money** | Never a bare number across the API boundary. Always `{ "amountMinor": "1234", "currency": "SAR" }`. |
| **Rate** | Stored as basis points. `aprBps: 1950` means `19.50%`. Never a float. |

**Rule:** no `float`, no `double`, no `Decimal`-in-JS. `0.1 + 0.2 !== 0.3` is not a theoretical concern in a ledger. It is a bug report.

---

## 3. Accounts

| Term | Definition |
|---|---|
| **Account** | A real-world container of money: a bank account, a credit card, a wallet, a loan. |
| **Account type** | `CURRENT`, `SAVINGS`, `CREDIT_CARD`, `CASH`, `LOAN`. `CURRENT` is deliberately not called `CHECKING`: "checking account" is North American. The display label is localised - "Cheque account" for `en-ZA`, "Current account" for `en-GB`. |
| **Opening balance** | The balance of the account on `openingDate`, before any transaction recorded in this app. A property of the Account, not a seeded transaction. |
| **Current balance** | **Derived, never stored:** `openingBalanceMinor + sum(transactions)`. Storing it is a cache, and caches drift. |
| **Sign convention** | `amountMinor > 0` means money **into** the account. `amountMinor < 0` means money **out of** the account. Holds for every account type. A credit card purchase is negative, so a card you owe on has a **negative balance**. |
| **Display sign** | The UI flips the sign for `CREDIT_CARD` and `LOAN` so users read "1,200 owed" rather than "-1,200". Display concern only; the stored value never flips. |

---

## 4. Categorisation

| Term | Definition |
|---|---|
| **Category** | A node in a two-level tree classifying transactions. Example: `Food` > `Groceries`. |
| **Parent category** | A depth-1 node with `parentId = null`. Carries the type. |
| **Child category** | A depth-2 node. Inherits its type from its parent. Cannot change type independently. |
| **Category type** | `INCOME` or `EXPENSE`. (`TRANSFER` reserved, not used in Phase 1.) |
| **Subcategory** | **Deprecated word. There is no `Subcategory` entity.** "Subcategory" in the original spreadsheet means a child Category. Say *child category*. |
| **Uncategorised** | A system-owned child category per type. Undeletable. The fallback for imports and quick entry. |

**Depth is capped at 2, deliberately.** The original offers about 50 subcategories in one flat list. A two-level tree reproduces the usability without inviting an unbounded taxonomy nobody maintains.

---

## 5. Transactions

| Term | Definition |
|---|---|
| **Transaction** | A single dated, recorded financial fact in one account. The atomic unit of the ledger. |
| **Ledger** | The set of all transactions in a workspace, presented as a filterable list. |
| **Transaction date** | The calendar date the money moved. A `DATE`, not a timestamp. It is not an instant and has no timezone. |
| **Created at** | When the row was written. A `TIMESTAMPTZ`. Never used in any financial calculation. |
| **Kind** | `INCOME`, `EXPENSE`, or `TRANSFER`. Must be consistent with the sign (invariant I7). |
| **Posted / Pending** | `Pending` means generated by a recurring rule and awaiting the user's confirmation. Phase 1 transactions are always `Posted`. |
| **Transfer** | **Not Phase 1.** Two linked transactions (one negative, one positive) sharing a `transferGroupId`. |
| **Split** | **Not planned.** One transaction, one category. Revisit as a separate entity only if genuinely demanded. |

**Terminology trap:** the original spreadsheet's "recurring transactions" tab is **not** a transaction table. It is a rule table. See section 6.

## 6. Recurrence

| Term | Definition |
|---|---|
| **Recurring rule** | A **template**, not a fact: amount, account, category, cadence, start and end dates, and a cadence anchor. Lives in `RecurringRule`. |
| **Cadence** | The repeat pattern, a closed enum: `DAILY`, `WEEKLY`, `BIWEEKLY`, `SEMIMONTHLY`, `MONTHLY`, `BIMONTHLY`, `QUARTERLY`, `SEMIANNUAL`, `ANNUAL`. Plus `interval`, meaning "every N cadences". |
| **Anchor** | The day-of-week or day-of-month fixing *which* date in each period. `MONTHLY` with anchor `31` is valid and must **clamp** to the last day of shorter months. Never skip, never overflow into the next month. |
| **Occurrence** | One iteration of a rule. The scheduler materialises it into a Transaction. |
| **Period key** | A stable string identifying an occurrence within its rule: `2026-03` (monthly), `2026-W14` (weekly), `2026-03-15` (daily), `2026` (annual). Unique together with `recurringRuleId` - this is what makes the scheduler idempotent. |
| **Materialise** | The act of turning a due occurrence into a Transaction row. |
| **`nextRunDate`** | The next date the scheduler should consider this rule. Advanced only inside the same transaction that materialises the occurrence. |
| **Auto-post vs confirm** | `autoPost = true` writes a `Posted` transaction. `false` writes a `Pending` one the user ticks off. The original's **"Paid" checkbox** is this second mode. |
| **RRULE** | **Not used.** RFC 5545 is far more expressive than this product needs, and far harder to reason about for clamping, month-ends and naive calendar dates. A closed enum is the better trade. |

## 7. Budgeting

| Term | Definition |
|---|---|
| **Budget period** | A calendar month within a year, identified as `(year, month)`. Owns the period's strategy. |
| **Budget line** | One `(budget period, category)` pair with a `limitMinor`. |
| **Budget strategy** | `ZERO_BASED` or `ROLLOVER`. Set on the period. |
| **Zero-based** | Every minor unit of expected income is assigned to a line. Unspent money does **not** carry forward at period end. |
| **Rollover** | Unspent, or overspent, balance on a line carries into the next period as `rolloverInMinor`. |
| **Actual** | The sum of transactions in a category within the period. Derived. |
| **Variance** | `limitMinor + rolloverInMinor - actualMinor`. Positive means remaining. Negative means overspent. |
| **Envelope** | **Marketing synonym for budget line. Do not use it in code.** |

---

## 8. Debt

| Term | Definition |
|---|---|
| **Debt** | **Not a table.** A debt **is an Account** of type `CREDIT_CARD` or `LOAN`, carrying a `DebtProfile`. One ledger, no duplication. |
| **Debt profile** | Payoff metadata attached to a debt account: `aprBps`, `minimumPaymentMinor`, `originalPrincipalMinor`, `strategy`. |
| **Snowball** | Pay off the **smallest balance first**. Psychologically motivated; ignores interest rate. |
| **Avalanche** | Pay off the **highest `aprBps` first**. Mathematically optimal; costs least interest. |
| **Custom** | A user-defined ordering of debt accounts. |
| **Extra payment** | `monthlySurplusMinor` - the amount above all minimums directed at the strategy's current target. |
| **Payoff schedule** | A simulated month-by-month projection: per-account balance, interest accrued, principal paid, and the debt-free date. **A projection, never persisted as transactions.** |
| **Minimum payment** | The contractual floor for a debt account each period. |

---

## 9. Savings

| Term | Definition |
|---|---|
| **Savings goal** | A target amount by an optional date. `kind = GOAL`. Example: "Wedding fund, 40,000 by 2027-06". |
| **Sinking fund** | A recurring earmark for a known, repeating future cost. `kind = SINKING_FUND`. Example: "Car insurance, 3,600 annually". |
| **Funded amount** | The derived sum of contributions. |
| **Contribution** | A transaction into the fund's account. There is no separate contribution table in v1 - the ledger is the source of truth. |

---

## 10. Productivity and lifestyle

| Term | Definition |
|---|---|
| **Task** | A discrete unit of work. |
| **Priority** | `URGENT`, `HIGH`, `MEDIUM`, `LOW`. |
| **Task status** | `PENDING`, `IN_PROGRESS`, `COMPLETED`, `DELAYED`. |
| **Delayed / overdue** | **Not stored.** `DELAYED` is **derived**: `dueDate < today AND status != COMPLETED`. Storing it creates rows that are correct on write and wrong by midnight. |
| **Project** | A grouping of tasks. No hierarchy. |
| **Habit** | A recurring behavioural commitment with a target frequency. |
| **Habit log** | A `(habit, date, state)` record. At most one per habit per day. |
| **Streak** | Consecutive satisfied periods, ending at the most recent period. **Derived on read**, never stored. |
| **Meal plan entry** | A `(week, dayOfWeek, mealType, text)` slot. |
| **Grocery item** | Something to buy. Either derived from meal entries or added manually. |

---

## 11. Cross-cutting

| Term | Definition |
|---|---|
| **Calendar** | A **read model**. A projection of tasks, recurring rules, habit logs and transactions onto dates. It owns no data. Nothing is ever written to it. |
| **Archive** | `archivedAt` is set. The row is retained, hidden from pickers and aggregates. Used for Accounts and Categories. |
| **Delete** | The row is removed. Used for Transactions, Tasks and Habit logs. |
| **Derived** | Computed on read from source-of-truth rows. Never cached in Phase 1. Every derived value is marked *derived* in the data model. |
| **Invariant** | A rule the data must always satisfy, enforced by a constraint or by a single guarded write path. |

---

## Words we do not use

`Subcategory` - say child category.
`Envelope` - say budget line.
`Bill` - a bill is an `EXPENSE` category plus a `RecurringRule`.
`Subscription` - same as a bill.
`Debt` as an entity - it is an Account with a DebtProfile.
`Balance` as a stored column - it is always derived.
`Overdue` as a stored status - it is always derived.
`Tab` - spreadsheet legacy. Say screen or view.
